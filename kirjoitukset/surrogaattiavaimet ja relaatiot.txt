Tiesittekö että tietovarastoissa INT-avaimilla toimivat relaatiot ovat isoilla datoilla HUOMATTAVASTI nopeampia kuin GUID-, VARCHAR- tai TIMESTAMP-yhteyksien kautta tehdyt relaatiot?

10 vuotta sitten kun aloitin urani BI:n parissa pääsin käyttämään analytiikkakerroksessa suoraan sellaista tietovarastoa jossa oli tähtimallin mukainen mallinnus tehtynä valmiiksi sisältäen kaikki "surrogaattiavaimet" ja "sentinel-rivit". En toki itse vielä silloin ymmärtänyt mitä nämä termit edes tarkoittavat, saati sitten miksi niin kannattaisi tehdä, mutta nykyään kun on pyörinyt jonkin aikaa skaalautuvan datan parissa syyt ovat selviä. Surrogaattiavaimet olivat kokonaislukuja ja INTEGER tallentuu pienempään tilaan kuin GUID- tai VARCHAR-avaimet, sekä "orporivit" aiheuttavat laskennallisia ongelmia. Nämä nopeusvaikutukset ja laskennalliset vaikeudet kun kerrotaan vielä rivien määrillä ja tehdyillä kyselyillä ovat erot skaalautuvuuteen valtavia.

Skaalautuvuus ei ole pelkästään sitä että ostetaan lisää kapasiteettia tai monistetaan yksi rakennettu ratkaisu sellaisenaan toiseen ympäristöön. Skaalautuminen on myös sitä että käytetään resursseja tehokkaasti, ja että minimoidaan "turha lisäarvoa tuottamaton käyttö". Käytännössä tämä voi tarkoittaa esimerkiksi sitä että mallinnetaan data niillä keinoilla jotka ovat todettu tehokkaimmiksi ja parhaimmiksi. Tämä onnistuu jopa sillä että tehdään arkkitehtuurisia päätöksiä jotka vaativat ylläpitoa, seurantaa ja governancea. Ne ovat niitä loppukäyttäjille näkymättömiä tylsiä toimenpiteitä jotka harvoin kiinostavat ketään, mutta jonkun olisi kuitenkin hyvä tarkkailla ratkaisujen kokonaisvaltaisen toimivuuden perään. 

GUID/VARCHAR → INT -muutokset joineissa ja vaikutukset nopeuteen isoissa tauluissa on esim. Snowflaken performanssiarkkitehdin mukaan vastaavanlainen:

"We can see from these results that using an integer data type for the join column (green) was the best choice for all queries, and by a significant margin. The varchar data type is nearly 2x to 3X slower than integer-only. "

https://medium.com/snowflake/data-type-considerations-for-join-keys-in-snowflake-304d515d2b91

Ja PostgreSQL:n puolella TIMESTAMP -> INT -muutokset sekä niiden vaikutukset nopeutuksiin ovat seuraavanlaiset:

Prosessi joka tehtiin:
• Obtain the current UTC time 
• Apply the current TAI–UTC offset (as of 2024: 37 seconds) 
• Convert to an integer-based format: -- Range query (ignoring leap seconds) SELECT * FROM scientific_data WHERE tai_time BETWEEN 2024010100000000000 AND 2024010200000000000;

The conducted analysis demonstrates that integer-based timestamp storage is an efficient methodology for modern time-series processing systems, combining high performance, precision, and resource efficiency. This approach provides significant performance improvements: 

• Insert operations accelerated by 35–50%;
• Query execution time reduced by 25–40%;

https://arxiv.org/pdf/2511.14502
